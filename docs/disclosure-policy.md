# ベースブレンド情報の開示ポリシー

最終更新: 2026年8月16日
対象: セレニアアロマ 運営者・認定インストラクター

## 結論

**3段階開示モデル**を採用する。

| 段階 | 対象 | 見える情報 |
|---|---|---|
| `public` | 利用者・未ログイン | ブレンド番号、仮名、**構成精油名**、香りの印象、香りの立ち方、目的、使うシーン、脳波測定との関係 |
| `instructor` | 認定インストラクター | 上記 + 他ブレンドとの使い分け、相性のよい追加精油とその理由、調合時の注意、事前確認が必要な方、測定値からの提案目安 |
| `internal` | 管理者（運営者本人） | 上記 + **内部配合比率**、作成メモ |

実装は `src/lib/disclosure.ts` の `DisclosureLevel` が正。

## なぜ構成精油名は公開するのか

### 1. 隠しても意味がない

アロマオイルの香りは、ある程度の知識があれば嗅ぎ分けられる。ラベンダーが入っているかどうかは、
香りを嗅げば分かる人には分かる。**隠せないものを隠していると表明すること自体が信頼を損なう。**

### 2. アレルギーと禁忌の説明ができなくなる

キク科アレルギーの方にローマンカモミール入りを渡す、妊娠中の方にクラリセージ入りを渡す、
といった事故は、成分を伝えていれば利用者本人が気付ける。成分を伏せる運用は、
この最後の安全弁を自ら外すことになる。**雑貨として販売していて表示義務がなくても、伝えるべき。**

### 3. インストラクターが売れなくなる

運営4名のうちアロマの知識があるのは1名。認定インストラクターは、自分が理解していない
ものを説明して売ることになる。「何が入っているか言えないが良いものです」という説明で
継続購入につなげるのは難しい。**成分名を言えることが、インストラクターの説明の土台になる。**

## なぜ内部比率は管理者限定なのか

比率こそがレシピの実体であり、事業の再現不可能性を担保している唯一の情報。
構成精油名（3種類）が分かっても、`8 : 3 : 1` と `1 : 3 : 8` では別物の香りになる。

- 精油名 = 「何を使っているか」→ 開示しても模倣されにくい
- 配合比率 = 「どう使っているか」→ 開示すると即座に模倣される

インストラクターにも開示しない理由は2つ。

1. **漏洩経路が人数分だけ増える。** 認定インストラクターは今後増える想定で、退会者も出る。
   比率を知った状態での退会は防げない。
2. **品質のばらつきが増える。** 比率を知ると「自分なりに調整」が始まる。
   ベースブレンドが同一であることが、セレニアアロマの品質保証になっている。

インストラクターには比率の代わりに**「使い分け指針」と「相性のよい追加精油」**を渡す。
現場で必要なのは比率そのものではなく「どのベースを選び、何を足すか」の判断材料であり、
これは比率を伏せたまま提供できる。

## 法的な位置づけ

本製品は**芳香用の雑貨**として販売している。この前提での注意点は次の通り。

- **成分表示義務はない。** 化粧品として届出していないため、全成分表示は求められない。
  上記の開示は法的義務ではなく、営業上・安全上の判断として行う。
- **効能効果をうたえない。** 「不眠が治る」「肌の老化を防ぐ」等は薬機法上の問題になる。
  本アプリの文言は「〜の場面で選ばれます」「〜と言われています」の範囲にとどめている。
  既存データの `benefits`（「疲労回復」「肌の老化防止」等）は目的カテゴリの内部分類であり、
  **販売ページや説明資料へそのまま転記しないこと。**
- **肌への塗布を案内しない。** 雑貨区分の製品を肌に使う案内は、化粧品としての効能標榜と
  見なされうる。現行のモックデータには「手首やデコルテになじませてください」等の記述が
  残っているため、実運用データでは芳香浴中心の表現に置き換えること（`usage_notes`）。

区分を化粧品へ移す場合は、全成分表示が必須になり上記の判断が変わる。その時点でこの文書を改訂する。

## 実装上の担保

比率を「UIで隠す」だけでは、開発者ツールから読めてしまう。以下の構成で担保している。

1. 比率データは `src/server/baseBlendPrivateRecipes.ts` に置き、`server-only` を import している。
   クライアントコンポーネントから参照するとビルドが失敗する。
2. 取得は `/api/base-blends/private` 経由のみ。このエンドポイントは呼び出し元の
   アクセストークンで Supabase に接続し、`base_blend_private_recipes` の RLS
   （管理者のみ）に判定を委ねる。サーバー側にサービスロールキーは置いていないため、
   RLS を迂回する経路が存在しない。
3. 画面側のフラグ（`showInternalRatios`）を書き換えても、API が比率を返さなければ何も表示されない。

以前はクライアントコードに管理者パスワードが直書きされていた（公開リポジトリのため誰でも読めた）。
この方式は廃止済み。
